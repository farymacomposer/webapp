# Use-Case: Завершить стрим

## Эндпоинт

- Метод: `POST`
- Путь: `/api/ComposerStream/CompleteStream`

## Что делает

Переводит стрим из `Live` в `Completed` и фиксирует время завершения (`CompletedAt = UtcNow`).

## Слои

- API:
  - требует авторизацию композитора (`AuthorizeComposer`);
  - принимает `CompleteStreamRequest`.
- Application (`ComposerStreamService`):
  - загружает стрим по `ComposerStreamId`;
  - допускает завершение только из `Live`;
  - при повторном вызове для `Completed` возвращает текущий стрим без изменений;
  - перед завершением проверяет ограничение по заказам в работе;
  - переводит стрим в `Completed`, выставляет `CompletedAt`, сохраняет изменения и публикует событие.

## Входные данные

- Body: `CompleteStreamRequest`
  - `ComposerStreamId` (`long`) - идентификатор стрима.

## Предусловия

- Пользователь должен быть авторизован как композитор.
- Стрим с указанным `ComposerStreamId` должен существовать.
- Стрим должен быть в статусе `Live`, либо уже быть `Completed` для идемпотентного повторного вызова.

## Что можно

- Завершить стрим в статусе `Live`.
- Повторно вызвать завершение для уже `Completed` стрима без побочных эффектов.

## Что нельзя

- Завершить несуществующий стрим.
- Завершить стрим в статусе `Planned` или `Canceled`.
- В целевом доменном описании: завершить стрим `S`, пока существует `ReviewOrder` со статусом `InProgress`, у которого `ProcessingStreamId == S`.

## Результат и постусловия

- Успешный ответ: `200 OK`.
- Тело: `CompleteStreamResponse`.
- После первого успешного завершения:
  - `Status = Completed`;
  - `CompletedAt` заполнено текущим UTC-временем.

## События и идемпотентность

- При первом успешном переходе в `Completed` публикуется `ComposerStreamChangedEvent` с типом `StreamCompleted`.
- Повторный вызов для уже `Completed` стрима идемпотентен:
  - состояние стрима не меняется;
  - событие повторно не публикуется.

## Ошибки

- Если стрим не найден или находится в недопустимом статусе, сервис выбрасывает `ComposerStreamException`, и API сейчас возвращает HTTP `666`.
- Если ограничение по заказам в работе нарушено, сервис выбрасывает `ComposerStreamException`, и API сейчас возвращает HTTP `666`.

## Текущая реализация vs целевое поведение

- Целевое правило: завершение стрима `S` должно блокироваться только заказом `InProgress`, который взят в работу именно на этом стриме, то есть `ProcessingStreamId == S`.
- Обратное следствие целевого правила: заказ `InProgress` на другом стриме не должен блокировать завершение `S`.
- Текущая реализация пока расходится с этим правилом: сервис вызывает `ReviewOrderQueries.FindInProgress()` без фильтра по стриму и поэтому блокирует завершение любого стрима, если в системе есть любой заказ в статусе `InProgress`.
