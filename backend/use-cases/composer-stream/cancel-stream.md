# Use-Case: Отменить стрим

## Эндпоинт

- Метод: `POST`
- Путь: `/api/ComposerStream/CancelStream`

## Что делает

Переводит стрим из `Planned` в `Canceled`.

## Слои

- API:
  - требует авторизацию композитора (`AuthorizeComposer`);
  - принимает `CancelStreamRequest`.
- Application (`ComposerStreamService`):
  - загружает стрим по `ComposerStreamId`;
  - допускает отмену только из `Planned`;
  - при повторном вызове для `Canceled` возвращает текущий стрим без изменений;
  - переводит стрим в `Canceled`, сохраняет изменения и публикует событие.

## Входные данные

- Body: `CancelStreamRequest`
  - `ComposerStreamId` (`long`) - идентификатор стрима.

## Предусловия

- Пользователь должен быть авторизован как композитор.
- Стрим с указанным `ComposerStreamId` должен существовать.
- Стрим должен быть в статусе `Planned`, либо уже быть `Canceled` для идемпотентного повторного вызова.

## Что можно

- Отменить стрим в статусе `Planned`.
- Повторно вызвать отмену для уже `Canceled` стрима без побочных эффектов.

## Что нельзя

- Отменить несуществующий стрим.
- Отменить стрим в статусе `Live` или `Completed`.
- В целевом доменном описании: отменить стрим, если с ним связан заказ в нетерминальном статусе.

## Результат и постусловия

- Успешный ответ: `200 OK`.
- Тело: `CancelStreamResponse`.
- После первого успешного вызова:
  - `Status = Canceled`.

## События и идемпотентность

- При первом успешном переходе в `Canceled` публикуется `ComposerStreamChangedEvent` с типом `StreamCanceled`.
- Повторный вызов для уже `Canceled` стрима идемпотентен:
  - состояние стрима не меняется;
  - событие повторно не публикуется.

## Ошибки

- Если стрим не найден или находится в недопустимом статусе, сервис выбрасывает `ComposerStreamException`, и API сейчас возвращает HTTP `666`.

## Текущая реализация vs целевое поведение

- Целевое правило: стрим нельзя отменить, если существует связанный с ним `ReviewOrder` в одном из нетерминальных статусов:
  - `Unspecified`;
  - `Preorder`;
  - `Pending`;
  - `InProgress`.
- Терминальными для этого ограничения считаются:
  - `Completed`;
  - `Canceled`.
- В текущем коде это правило не реализовано: `ComposerStreamService.Cancel()` не проверяет наличие связанных заказов перед отменой.
- Критерий технической связи заказа со стримом требует отдельного явного выравнивания в коде и документации; текущий use case фиксирует именно доменное правило запрета, а не конкретный SQL/EF-фильтр.
