# Use-Case: Поднять заказ в очереди

## Эндпоинт

- Метод: `POST`
- Путь: `/api/ReviewOrder/MoveUpReviewOrder`

## Что делает

Добавляет платеж к существующему заказу, чтобы повысить его приоритет в очереди.

## Слои

- API:
  - требует роль администратора (`AuthorizeAdmins`);
  - требует заголовок `Idempotency-Key`;
  - принимает `MoveUpReviewOrderRequest`;
  - валидирует `Nickname`, `PaymentAmount` и `TopUpProvider`.
- Application (`ReviewOrderService`):
  - находит пользователя из токена;
  - загружает заказ;
  - допускает операцию только для `Preorder` и `Pending`;
  - создает пополнение и платеж;
  - сохраняет изменения и публикует событие.

## Входные данные

- Заголовок: `Idempotency-Key` (`Guid`), обязателен.
- Body: `MoveUpReviewOrderRequest`
  - `ReviewOrderId`.
  - `Nickname` - от 1 до 40 символов.
  - `PaymentAmount` - строго больше `0`.
  - `TopUpProvider` - один из `Donationalerts`, `Donatty`, `TwitchChannelPoints`, `Manual`.

## Предусловия

- Пользователь должен быть авторизован как администратор.
- Пользователь из токена должен существовать.
- Заказ должен существовать и быть в статусе `Preorder` или `Pending`.

## Что можно

- Поднять заказ в статусе `Preorder` или `Pending`.
- Выполнить операцию с созданием пополнения и платежной транзакции.

## Что нельзя

- Поднимать несуществующий заказ.
- Поднимать заказ в статусах `InProgress`, `Completed`, `Canceled`.
- Передавать сумму `<= 0`.
- Передавать неподдерживаемый провайдер пополнения.

## Результат и постусловия

- Успешный ответ: `200 OK`.
- Тело: `MoveUpReviewOrderResponse`.
- Клиент получает:
  - `ReviewOrder: ReviewOrderDto`;
  - `PaymentTransactionId: long`.
- Позиция заказа в очереди меняется не напрямую полем в DTO, а через созданный платеж и последующий пересчет/обновление очереди.

## События и идемпотентность

- Идемпотентность обеспечивается фильтром `[Idempotent]` в рамках пользователя, маршрута и `Idempotency-Key`.
- При успешном вызове публикуется `ReviewOrderChangedEvent`:
  - `UpdateType = OrderMovedUp`;
  - `PreviousStatus =` исходный статус заказа.

## Ошибки

- Некорректный запрос не проходит API-валидацию:
  - сумма `<= 0`;
  - неподдерживаемый `TopUpProvider`;
  - невалидный nickname.
- Если пользователь не найден или заказ находится в недопустимом статусе, сервис выбрасывает `ReviewOrderException`, и API сейчас возвращает HTTP `666`.

## Текущая реализация vs целевое поведение

- Существенных расхождений между документируемым поведением и текущей реализацией для этого сценария нет.
- Изменение позиции заказа в очереди происходит опосредованно через платеж и обновление очереди, а не через отдельное поле ответа.
