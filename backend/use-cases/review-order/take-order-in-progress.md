# Use-Case: Взять заказ в работу

## Эндпоинт

- Метод: `POST`
- Путь: `/api/review-orders/take-in-progress`

## Что делает

Переводит заказ в `InProgress`, фиксирует время начала и связывает его с активным стримом обработки.

## Слои

- API:
  - требует роль администратора (`AuthorizeAdmins`);
  - принимает `TakeOrderInProgressRequest`.
- Application (`ReviewOrderService`):
  - загружает заказ;
  - допускает операцию только для `Pending`, если заказ не заморожен;
  - требует существующий `Live` стрим;
  - требует отсутствие другого заказа в `InProgress`;
  - вычисляет текущую позицию в очереди;
  - сохраняет `QueueCategory`, `ProcessingStream`, `Status = InProgress`, `InProgressAt`;
  - сохраняет изменения и публикует событие.

## Входные данные

- Body: `TakeOrderInProgressRequest`
  - `ReviewOrderId`.

## Предусловия

- Пользователь должен быть авторизован как администратор.
- Заказ должен существовать.
- Должен существовать активный стрим (`Live`).
- Не должно быть другого заказа в работе.

## Что можно

- Взять в работу заказ в статусе `Pending`, если он не заморожен.
- Повторно вызвать сценарий для уже `InProgress` заказа без побочных эффектов.

## Что нельзя

- Взять несуществующий заказ.
- Взять заказ не в статусе `Pending`, включая `Preorder` и `AwaitingPayment`.
- Взять замороженный заказ.
- Взять заказ вне активного (`Live`) стрима.
- Взять второй заказ, пока другой уже находится в `InProgress`.

## Результат и постусловия

- Успешный ответ: `200 OK`.
- Тело: `TakeOrderInProgressResponse`.
- Клиент получает `ReviewOrderDto`.
- Публичный API-контракт не возвращает `ProcessingStream` или `QueueCategory`.
- Внутренние postconditions application-слоя:
  - `Status = InProgress`;
  - `InProgressAt` заполнено;
  - `ProcessingStream` установлен в текущий `Live` стрим;
  - `QueueCategory` вычислен из текущей позиции в очереди.

## События и идемпотентность

- Повторный вызов для уже `InProgress` заказа идемпотентен:
  - persisted-состояние не меняется;
  - событие повторно не публикуется.
- При первом успешном вызове публикуется `ReviewOrderChangedEvent`:
  - `UpdateType = OrderTaken`;
  - `PreviousStatus =` исходный статус заказа.

## Ошибки

- Если заказ не найден, заморожен, находится в недопустимом статусе, активный стрим отсутствует или уже есть другой заказ в работе, сервис выбрасывает `ReviewOrderException`, и API сейчас возвращает HTTP `666`.

## Текущая реализация vs целевое поведение

- Целевое правило: в работу можно брать только заказ, который по графу активности очереди находится в `Active`.
- `AwaitingPayment` виден в очереди как активная позиция, но взять его в работу нельзя, пока обязательная стоимость не покрыта и persisted-статус не стал `Pending`.
- Это означает, что переход `Scheduled -> InProgress` должен быть запрещен.
- Текущая реализация пока расходится с этим правилом: код проверяет только `ReviewOrder.Status == Pending`, `!IsFrozen`, наличие `Live` стрима и отсутствие другого `InProgress`, но не проверяет, что текущая активность заказа не равна `Scheduled`.
- Внутреннее поле называется `QueueCategory`, а не `CategoryType`; это не часть `ReviewOrderDto`.
