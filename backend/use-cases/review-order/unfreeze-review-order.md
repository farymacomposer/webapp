# Use-Case: Разморозить заказ

## Эндпоинт

- Метод: `POST`
- Путь: `/api/review-orders/unfreeze`

## Что делает

Выключает флаг заморозки заказа (`IsFrozen = false`), возвращая его к обычной обработке очереди.

## Слои

- API:
  - требует роль администратора (`AuthorizeAdmins`);
  - принимает `UnfreezeReviewOrderRequest`.
- Application (`ReviewOrderService`):
  - загружает заказ;
  - допускает разморозку только для `Preorder`, `Pending` и `AwaitingPayment`;
  - выставляет `IsFrozen = false`;
  - сохраняет изменения и публикует событие.

## Входные данные

- Body: `UnfreezeReviewOrderRequest`
  - `ReviewOrderId`.

## Предусловия

- Пользователь должен быть авторизован как администратор.
- Заказ должен существовать и быть в допустимом статусе.

## Что можно

- Разморозить заказ в статусе `Preorder`, `Pending` или `AwaitingPayment`.
- Повторно вызвать сценарий для уже размороженного заказа без побочных эффектов.

## Что нельзя

- Разморозить несуществующий заказ.
- Разморозить заказ в `InProgress`, `Completed` или `Canceled`.

## Результат и постусловия

- Успешный ответ: `200 OK`.
- Тело: `UnfreezeReviewOrderResponse`.
- Клиент получает `ReviewOrderDto`.
- После первого успешного вызова:
  - `IsFrozen = false`.
- `ReviewOrder.Status` при этом не меняется.

## События и идемпотентность

- Повторный вызов для уже размороженного заказа идемпотентен:
  - persisted-состояние не меняется;
  - событие повторно не публикуется.
- При первом успешном вызове публикуется `ReviewOrderChangedEvent`:
  - `UpdateType = OrderUnfrozen`;
  - `PreviousStatus =` исходный статус заказа.

## Ошибки

- Если заказ не найден или находится в недопустимом статусе, сервис выбрасывает `ReviewOrderException`, и API сейчас возвращает HTTP `666`.

## Текущая реализация vs целевое поведение

- `UnfreezeReviewOrder` не меняет persisted-статус `ReviewOrder.Status`.
- После пересчета очереди вычисляемая активность заказа должна вернуться в `Active` или `Scheduled` в зависимости от ближайшего доступного стрима.
