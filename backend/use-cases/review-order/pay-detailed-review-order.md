# Use-Case: Оплатить подробный разбор заказа

## Эндпоинт

- Метод: `POST`
- Путь: `/api/review-orders/pay-detailed-review`

## Что делает

Создает отдельную платную услугу подробного разбора для существующего заказа.
Стоимость услуги фиксированная и рассчитывается на сервере из настроек приложения.

## Слои

- API:
  - требует роль администратора (`AuthorizeAdmins`);
  - требует заголовок `Idempotency-Key`;
  - принимает `PayDetailedReviewOrderRequest`;
  - валидирует `ReviewOrderId`, `Nickname` и `TopUpProvider`.
- Application (`ReviewOrderService`):
  - находит пользователя из токена;
  - загружает заказ;
  - проверяет, что подробный разбор еще не оплачен;
  - берет стоимость из `ReviewOrderDetailedReviewAmount`;
  - создает пополнение, источник услуги и платеж;
  - сохраняет изменения и публикует событие.

## Входные данные

- Заголовок: `Idempotency-Key` (`Guid`), обязателен.
- Body: `PayDetailedReviewOrderRequest`
  - `ReviewOrderId` - строго больше `0`.
  - `Nickname` - от 1 до 40 символов.
  - `TopUpProvider` - один из `Donationalerts`, `Donatty`, `TwitchChannelPoints`, `Manual`.

## Предусловия

- Пользователь должен быть авторизован как администратор.
- Пользователь из токена должен существовать.
- Заказ должен существовать.
- `ReviewOrderDetailedReviewAmount` должен быть больше `0`.

## Что можно

- Оплатить подробный разбор для существующего заказа.
- Выполнить операцию с созданием пополнения и платежной транзакции.
- Оплатить услугу один раз для одного заказа.

## Что нельзя

- Оплачивать подробный разбор для несуществующего заказа.
- Оплачивать подробный разбор повторно.
- Оплачивать услугу, если фиксированная стоимость в настройках `<= 0`.
- Передавать неподдерживаемый провайдер пополнения.

## Результат и постусловия

- Успешный ответ: `200 OK`.
- Тело: `PayDetailedReviewOrderResponse`.
- Клиент получает:
  - `ReviewOrder: ReviewOrderDto`;
  - `PaymentTransactionId: long`.
- Создается `ReviewOrderDetailedReviewPaymentEntity` как отдельный источник транзакции.
- Создается `AccountTopUp` на фиксированную стоимость услуги.
- Создается `Payment` на источник услуги.
- Платеж за подробный разбор не входит в обязательную checkout-стоимость заказа и не повышает `PaidPriorityAmount`; legacy `ReviewOrderDto.TotalAmount` совпадает с `PaidPriorityAmount`.

## События и идемпотентность

- Идемпотентность обеспечивается фильтром `[Idempotent]` в рамках пользователя, маршрута и `Idempotency-Key`.
- При успешном вызове публикуется `ReviewOrderChangedEvent`:
  - `UpdateType = OrderMovedUp`;
  - `PreviousStatus =` исходный статус заказа.

## Ошибки

- Некорректный запрос не проходит API-валидацию:
  - `ReviewOrderId <= 0`;
  - невалидный nickname;
  - неподдерживаемый `TopUpProvider`.
- Если пользователь не найден, заказ не найден, услуга уже оплачена или фиксированная стоимость `<= 0`, сервис выбрасывает `ReviewOrderException`, и API сейчас возвращает HTTP `666`.

## Текущая реализация vs целевое поведение

- Сумма услуги не передается клиентом и рассчитывается сервером из `ReviewOrderDetailedReviewAmount`.
- Текущая реализация не ограничивает оплату по persisted-статусу заказа; решающими условиями являются наличие заказа, положительная стоимость и отсутствие ранее оплаченной услуги.
