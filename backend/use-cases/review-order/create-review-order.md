# Use-Case: Создать заказ

## Эндпоинт

- Метод: `POST`
- Путь: `/api/ReviewOrder/CreateReviewOrder`

## Что делает

Создает заказ на разбор трека выбранного типа и привязывает его к подходящему стриму.
Выбор стрима зависит от типа заказа и истории заказов ника.

## Слои

- API:
  - требует роль администратора (`AuthorizeAdmins`);
  - требует заголовок `Idempotency-Key`;
  - принимает `CreateReviewOrderRequest`;
  - валидирует nickname, тип заказа, `TrackUrl`, суммы и `TopUpProvider`.
- Application (`ReviewOrderService`):
  - находит пользователя из токена;
  - выбирает подходящий стрим в зависимости от типа заказа;
  - создает заказ;
  - для `Donation` дополнительно создает пополнение и платеж;
  - сохраняет изменения и публикует событие.
- Infrastructure (`ReviewOrderStore`):
  - создает заказ со статусом `Preorder`, если `TrackUrl` не передан;
  - создает заказ со статусом `Pending`, если `TrackUrl` передан.

## Входные данные

- Заголовок: `Idempotency-Key` (`Guid`), обязателен.
- Body: `CreateReviewOrderRequest`
  - `Nickname` - от 1 до 40 символов.
  - `OrderType` - один из поддерживаемых типов: `Donation`, `OutOfQueue`, `Free`, `Charity`.
  - `TrackUrl` - опциональный валидный URL.
  - `PaymentAmount` - обязателен для `Donation`, для остальных типов должен быть `0` или отсутствовать.
  - `TopUpProvider` - обязателен для `Donation`; поддерживаются `Donationalerts`, `Donatty`, `TwitchChannelPoints`, `Manual`.
  - `UserComment` - до 200 символов.

## Предусловия

- Пользователь должен быть авторизован как администратор.
- Пользователь из токена должен существовать.
- Для выбранного типа заказа должен существовать подходящий стрим.

## Что можно

- Создать заказ типа `OutOfQueue`, `Donation`, `Free` или `Charity`.
- Создать `Preorder`, если `TrackUrl` не передан.
- Создать `Pending`, если `TrackUrl` передан.
- Для `Donation` выполнить создание заказа вместе с финансовыми транзакциями.
- Для `Donation` и `Free`:
  - если у ника уже были заказы, использовать ближайший стрим типа `Donation`;
  - если заказов у ника еще не было, использовать ближайший доступный стрим.
- Для `OutOfQueue` использовать ближайший доступный стрим.
- Для `Charity` создать заказ только на активном благотворительном стриме.

## Что нельзя

- Передавать неподдерживаемый тип заказа.
- Для `Donation` не передавать сумму или провайдера пополнения.
- Для `Donation` передавать сумму `<= 0`.
- Для `Free`, `OutOfQueue` и `Charity` передавать ненулевую сумму.
- Создать заказ без подходящего стрима.
- Создать `Charity` заказ, если активного благотворительного стрима нет.

## Результат и постусловия

- Успешный ответ: `200 OK`.
- Тело: `CreateReviewOrderResponse`.
- Клиент получает `ReviewOrderDto`.
- После успешного вызова persisted-статус нового заказа:
  - `Preorder`, если `TrackUrl` не передан;
  - `Pending`, если `TrackUrl` передан.

## События и идемпотентность

- Идемпотентность обеспечивается фильтром `[Idempotent]` в рамках пользователя, маршрута и `Idempotency-Key`.
- При успешном создании публикуется `ReviewOrderChangedEvent`:
  - `UpdateType = OrderCreated`;
  - `PreviousStatus = Unspecified`.
- Значение `PreviousStatus = Unspecified` относится к событию, а не к persisted-статусу уже созданного заказа.

## Ошибки

- Некорректный запрос не проходит API-валидацию:
  - неподдерживаемый тип;
  - невалидная сумма;
  - невалидный `TopUpProvider`;
  - невалидный `TrackUrl`;
  - слишком длинный `UserComment`.
- Если пользователь не найден или нет подходящего стрима, сервис выбрасывает `ReviewOrderException`, и API сейчас возвращает HTTP `666`.

## Текущая реализация vs целевое поведение

- Существенных расхождений между документируемым HTTP-контрактом и текущим кодом для этого сценария нет.
- Важно не путать статус заказа после создания с event-полем `PreviousStatus = Unspecified`.
