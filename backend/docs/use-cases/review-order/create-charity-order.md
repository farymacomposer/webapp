# Use case: Создать благотворительный заказ

## Полезный результат

На текущем благотворительном стриме появляется заказ на разбор: без оплаты, сразу привязанный к этому стриму. Администратор может принять его в работу на этом стриме.

## Участник и момент запуска

- Участник: администратор
- Триггер: на благотворительном стриме нужно завести заказ на разбор
- Предусловия: администратор аутентифицирован; есть стрим со статусом Live и типом Charity

## Входные данные

- `UserNickname` — псевдоним зрителя. Обязателен, от 1 до 40 символов. Если такого ника ещё нет, он создаётся
- `UserComment` — комментарий зрителя. Необязателен, до 200 символов
- `TrackUrl` — ссылка на трек. Необязательна, если задана — должна быть корректным URL
- `TrackDurationSeconds` — длительность трека в секундах. Необязательна, если задана — от 1 секунды до 15 минут
- Ссылка и длительность либо оба заданы, либо оба отсутствуют

Сумма и канал поступления денег во вход не входят.

## Наблюдаемый результат

При успехе:

- Создан заказ типа Charity на запущенном благотворительном стриме
- К оплате 0; в ответе денежная сумма заказа 0
- Если ссылки на трек нет — статус Preorder. Если ссылка и длительность заданы — статус Pending
- Номинальная цена заказа записана из настроек, но не предъявляется к оплате
- Категория в очереди не задана; заказ не заморожен
- Если ника не было — он создан и привязан к заказу
- Очередь узнаёт о новом заказе
- Возвращается созданный заказ

При невозможности выполнения:

- Нет стрима со статусом Live и типом Charity (в том числе если есть только запланированный благотворительный или запущенный стрим другого типа) → заказ не создан, ответ «Нет запущенного благотворительного стрима»
- Некорректный ник, комментарий, ссылка, длительность или пара «ссылка / длительность» → заказ не создан, ошибка валидации
- Участник не администратор → заказ не создан, отказ в доступе

## Бизнес-правила

1. Благотворительный заказ создаётся только пока идёт благотворительный стрим. Ближайший запланированный благотворительный стрим для создания не подходит.
2. Стрим выбирается только по факту «сейчас Live и Charity». История заказов ника на выбор стрима не влияет.
3. Заказ не требует и не принимает денежную оплату: к оплате 0, тип Charity оплату не поддерживает.
4. Благотворительный заказ не входит в категории вне очереди, донат и долг. После создания он не занимает активную позицию в приоритетной очереди этих категорий. Это не мешает взять его в работу отдельной операцией: схема категорий описывает только приоритет активных.
5. Повторный запрос: без того же ключа идемпотентности каждый вызов создаёт новый заказ. С тем же ключом и тем же телом в течение часа возвращается прежний успешный ответ, новый заказ не создаётся.

## Различающие сценарии

- Если благотворительный стрим запущен — заказ создаётся на нём. Если он только запланирован или запущен стрим другого типа — заказ не создаётся.
- Если ссылки на трек нет — заказ в Preorder и его ещё нельзя взять в работу. Если ссылка и длительность заданы — заказ в Pending и его можно взять в работу, хотя в активных категориях его нет.
- Донатный, бесплатный и внеочередной заказы этим use case не создаются: у них другой тип, другое назначение на стрим и другие правила оплаты.

## Принятые ограничения

- Бизнес-ограничения: заказ бесплатный для зрителя в рамках этого сценария; деньги на благотворительность этим use case не проводятся
- Технические ограничения: операция идемпотентна по заголовку ключа; создание и публикация в очередь после успешного сохранения
- Вне scope: оплата заказа; создание заказов других типов; взятие в работу, добавление ссылки, отмена, заморозка; запуск и планирование благотворительного стрима

## Основания спецификации

### Решения

- Описать существующую операцию создания благотворительного заказа.
- Схема статусов активности и категорий описывает только приоритет активных. Благотворительный заказ в эти категории не входит, но это не запрещает взять его в работу.

### Факты

- Операция уже реализована: `ReviewOrderController.CreateCharity` → `CreateCharityHandler`
- Стрим: только `GetLiveCharityStream` — Live и Charity, иначе «Нет запущенного благотворительного стрима»
- Заказ создаётся с типом Charity, `payableAmount = 0`, ценой `ReviewOrderNominalPrice`
- Статус: Preorder без ссылки, Pending при ссылке
- `ReviewOrderEntity.Pay` отклоняет Charity; `GetTotalAmount` и `GetPaidPriorityAmount` для Charity равны 0
- Приоритетная очередь учитывает только OutOfQueue, Donation и Free
- Валидация входа: `CreateRequestBase` и `CreateCharityRequest`
- Тестов на создание благотворительного заказа нет

### Предположения

- Одновременно существует не больше одного запущенного благотворительного стрима; при нескольких берётся первый найденный
- Номинальная цена хранится для единообразия с другими заказами и не означает долг зрителя

### Открытые вопросы

- Нет вопросов, которые меняют наблюдаемый результат создания

## Примеры приёмки

### Заказ со ссылкой на запущенном благотворительном стриме

Дано:

- идёт благотворительный стрим
- ника `viewer` ещё нет

Когда:

- администратор создаёт благотворительный заказ: ник `viewer`, трек и длительность 180 секунд

Тогда:

- создан заказ типа Charity в статусе Pending
- ник `viewer` создан и указан как основной
- заказ привязан к этому благотворительному стриму
- к оплате 0, денежная сумма в ответе 0
- заказ можно взять в работу, хотя в активных категориях его нет

### Предзаказ без трека

Дано:

- идёт благотворительный стрим

Когда:

- администратор создаёт благотворительный заказ только с ником

Тогда:

- создан заказ типа Charity в статусе Preorder
- ссылка и длительность пустые
- к оплате 0
- заказ нельзя взять в работу, пока не появится ссылка на трек

### Нет запущенного благотворительного стрима

Дано:

- благотворительный стрим запланирован, но не запущен
- или запущен только донатный / долговой стрим

Когда:

- администратор создаёт благотворительный заказ

Тогда:

- заказ не создан
- ответ: нет запущенного благотворительного стрима

### Повтор с тем же ключом идемпотентности

Дано:

- благотворительный заказ уже создан по ключу K

Когда:

- администратор повторяет тот же запрос с ключом K

Тогда:

- новый заказ не создан
- возвращается прежний успешный ответ

## Техническая привязка — опционально

- Точка входа: `POST api/ReviewOrder/CreateCharity`
- Авторизация: роль администратора
- Транзакционная граница: сохранение заказа, затем событие `OrderCreated` в канал очереди
- Идемпотентность: заголовок `Idempotency-Key`, окно 1 час, повтор того же тела возвращает сохранённый ответ
- Изменяемые данные: `ReviewOrders`; при новом нике — `UserNicknames`
- Публикуемые события: `OrderQueueEventChannel` / `OrderCreated`
- Требования к консистентности: заказ не существует без сохранённой записи; очередь обновляется после сохранения
