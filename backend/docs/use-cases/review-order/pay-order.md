# Use case: Оплатить заказ

## Полезный результат

На заказ разбора трека зачисляется очередной денежный платёж. Для доната этого может хватить, чтобы заказ стал готов к взятию в работу; для бесплатного заказа меняется только место в очереди.

## Участник и момент запуска

- Участник: администратор
- Триггер: регистрация уже полученного платежа в пользу существующего заказа
- Предусловия: заказ существует; его тип поддерживает денежную оплату (`Donation` или `Free`); статус — `Preorder`, `AwaitingPayment` или `Pending`

## Входные данные

- `ReviewOrderId` — идентификатор заказа, строго больше 0
- `Nickname` — псевдоним плательщика, 1–40 символов; пробелы по краям отбрасываются. Ник создаётся, если его ещё нет
- `PaymentAmount` — сумма платежа, строго больше 0
- `TopUpProvider` — канал, через который деньги уже поступили: `Donationalerts`, `Donatty`, `TwitchChannelPoints` или `Manual`

## Наблюдаемый результат

При успехе:

- счёт ника пополняется на `PaymentAmount` через указанный канал и сразу на ту же сумму списывается как оплата заказа; чистый баланс счёта не меняется
- платёж накапливается на заказе и учитывается в оплаченной сумме для приоритета очереди
- `MainNickname` и список ников заказа не меняются
- заморозка не меняется
- очередь пересчитывает позицию заказа
- возвращается актуальное состояние заказа

Для `Donation` дополнительно:

- `PayableAmount` и статус пересчитываются по требуемой сумме за текущую длительность трека
- нет ссылки на трек → статус остаётся `Preorder`
- ссылка есть и оплаты недостаточно → статус `AwaitingPayment`, в `PayableAmount` — остаток
- ссылка есть и оплаты достаточно → статус `Pending`, `PayableAmount = 0`

Для `Free` дополнительно:

- статус и `PayableAmount` не меняются
- заказ продвигается в очереди за счёт выросшей оплаченной суммы

При невозможности выполнения:

- заказ не найден → ошибка «заказ не найден»
- статус не `Preorder` / `AwaitingPayment` / `Pending` → ошибка «невозможно оплатить заказ»; платёж не создаётся
- тип не `Donation` и не `Free` → ошибка «тип заказа не поддерживает денежную оплату»; платёж не создаётся
- `PaymentAmount` ≤ 0 → запрос отклоняется
- канал пополнения не из допустимого набора → запрос отклоняется

## Бизнес-правила

1. Операция регистрирует факт поступления денег, а не списывает ранее накопленный баланс ника: пополнение и оплата всегда на одну и ту же сумму.
2. Плательщиком может быть любой ник, не только создатель заказа. Ник к заказу не привязывается.
3. Заморозка оплату не запрещает и самой оплатой не снимается.
4. Требуемая сумма для доната: номинальная цена заказа плюс доплата за каждую секунду трека сверх включённой длительности. Если длительности нет, доплаты за сверхлимит нет — остаётся номинал.
5. Оплата сверх требуемого для доната допустима: статус `Pending`, `PayableAmount = 0`, лишнее увеличивает приоритет в очереди.
6. Для `Free` деньги не создают и не закрывают задолженность: `PayableAmount` остаётся прежним (обычно 0), статус не переводится в `AwaitingPayment` и не выводится из него.
7. Оплата подробного разбора — отдельная операция и в этот use case не входит.
8. Повторный запрос: каждый успешный вызов с новой суммой — ещё один платёж, суммы на заказе складываются. Повтор с тем же ключом идемпотентности и тем же телом не создаёт второй платёж.

## Различающие сценарии

- Если донат со ссылкой на трек и накопленных оплат ещё не хватает, система оставляет `AwaitingPayment` и уменьшает `PayableAmount`.
- Если донат со ссылкой на трек и накопленных оплат хватает (в том числе с переплатой), система ставит `Pending` и обнуляет `PayableAmount`.
- Если бесплатный заказ в `Pending` и приходит любая сумма, система оставляет `Pending` и `PayableAmount = 0`; меняется только приоритет в очереди.
- Если заказ заморожен, оплата проходит по тем же правилам, что и для незамороженного; признак заморозки сохраняется.

## Принятые ограничения

- Бизнес-ограничения: для `Free` платёж только двигает очередь; статус и `PayableAmount` не пересчитываются
- Технические ограничения: авторизация администратора; идемпотентность по заголовку ключа
- Вне scope: создание заказа; смена ссылки на трек; оплата подробного разбора; взятие в работу, выполнение, отмена, заморозка и разморозка; возврат платежа

## Основания спецификации

### Решения

- Для `Free` деньги только двигают очередь: статус не меняется, `PayableAmount` не меняется

### Факты

- HTTP `POST api/ReviewOrder/Pay`, роль администратора, ключ идемпотентности
- Обработчик создаёт пополнение счёта и платёж на заказ, затем вызывает доменный `Pay`
- Доменный `Pay` сейчас пересчитывает статус и `PayableAmount` одинаково для `Donation` и `Free`; для `Free` это расходится с принятым правилом
- Денежная оплата в домене разрешена только для `Donation` и `Free` и только в `Preorder` / `AwaitingPayment` / `Pending`
- Требуемая сумма считается по номиналу и сверхлимитным секундам трека
- Ник плательщика ищется или создаётся; к `UserNicknames` заказа не добавляется
- После сохранения публикуется событие очереди `OrderMovedUp`

### Предположения

- Если бесплатный заказ оказался в `AwaitingPayment` из-за другой операции, этот use case всё равно не меняет его статус и `PayableAmount`

### Открытые вопросы

- Нет

## Примеры приёмки

### Донат: доплата закрывает задолженность

Дано:

- заказ типа `Donation`, есть ссылка на трек, статус `AwaitingPayment`, `PayableAmount = 400`, уже оплачено 600 при требуемых 1000

Когда:

- администратор регистрирует платёж на 400

Тогда:

- на заказе ещё один платёж 400
- статус `Pending`, `PayableAmount = 0`
- очередь пересчитана

### Донат: оплаты всё ещё недостаточно

Дано:

- заказ типа `Donation`, есть ссылка на трек, статус `AwaitingPayment`, `PayableAmount = 400`

Когда:

- администратор регистрирует платёж на 100

Тогда:

- статус остаётся `AwaitingPayment`
- `PayableAmount = 300`
- платёж 100 учтён

### Донат без ссылки на трек

Дано:

- заказ типа `Donation` без ссылки, статус `Preorder`, `PayableAmount = 1000`, оплат нет

Когда:

- администратор регистрирует платёж на 400

Тогда:

- статус остаётся `Preorder`
- `PayableAmount = 600`
- платёж 400 учтён

### Бесплатный заказ: любая сумма только двигает очередь

Дано:

- заказ типа `Free`, есть ссылка на трек, статус `Pending`, `PayableAmount = 0`, оплат нет

Когда:

- администратор регистрирует платёж на 100 (меньше номинала за длительность)

Тогда:

- статус остаётся `Pending`
- `PayableAmount` остаётся 0
- платёж 100 учтён и поднимает заказ в очереди

### Замороженный донат можно оплатить

Дано:

- заказ типа `Donation`, `IsFrozen = true`, статус `AwaitingPayment`

Когда:

- администратор регистрирует допустимый платёж, которого хватает

Тогда:

- статус становится `Pending`
- `IsFrozen` остаётся `true`

### Тип без денежной оплаты

Дано:

- заказ типа `Charity` или `OutOfQueue`

Когда:

- администратор пытается зарегистрировать платёж

Тогда:

- ошибка «тип заказа не поддерживает денежную оплату»
- транзакций нет, заказ не изменён

### Заказ уже в работе

Дано:

- заказ в статусе `InProgress`

Когда:

- администратор пытается зарегистрировать платёж

Тогда:

- ошибка «невозможно оплатить заказ»
- транзакций нет, заказ не изменён

## Техническая привязка — опционально

- Точка входа: `ReviewOrderController.Pay` → `PayHandler`
- Авторизация: `[AuthorizeAdmins]`
- Транзакционная граница: `SaveChangesAsync` после пополнения, платежа и доменного `Pay`; создание нового ника сохраняется раньше
- Идемпотентность: `[Idempotent]`, заголовок ключа
- Изменяемые данные: транзакции пополнения и оплаты; для `Donation` — `Status`, `PayableAmount`; для `Free` — только транзакции
- Публикуемые события: `OrderQueueUpdateType.OrderMovedUp`
- Требования к консистентности: доменный `Pay` для `Free` не должен вызывать общий пересчёт статуса и `PayableAmount`
