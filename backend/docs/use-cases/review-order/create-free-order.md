# Use case: Создать бесплатный заказ

## Полезный результат

Администратор дарит зрителю разбор трека. В системе появляется бесплатный заказ на разбор: деньги не проводятся, покрытие фиксируется выдачей и сразу погашением жетона, заказ привязывается к стриму и попадает в ту же очередь, что и донатные.

## Участник и момент запуска

- Участник: администратор (композитор или модератор)
- Триггер: нужно завести заказ без оплаты — подарок, компенсация или иное решение администрации
- Предусловия:
  - участник аутентифицирован как администратор
  - есть ближайший доступный стрим для назначения заказу (см. правило назначения стрима)

## Входные данные

- `UserNickname` — псевдоним зрителя, на которого оформляется заказ. Обязателен, 1–40 символов. Поиск существующего ника без учёта регистра.
- `UserComment` — необязательный комментарий зрителя, до 200 символов.
- `TrackUrl` — необязательная ссылка на трек. Если задана, должна быть корректным URL.
- `TrackDurationSeconds` — необязательная длительность трека в секундах. Если задана, от 1 секунды до 15 минут.
- ключ идемпотентности — обязателен; повтор того же запроса с тем же ключом не создаёт второй заказ.

Ссылка на трек и длительность либо оба заданы, либо оба отсутствуют.

Сумма платежа и канал поступления не передаются: этот use case деньги не принимает.

## Наблюдаемый результат

При успехе:

- создаётся заказ типа «бесплатный», не замороженный, без категории очереди
- заказ привязан к выбранному стриму создания и к нику зрителя; ник становится основным
- цена заказа равна номинальной цене из настроек; сумма к доплате 0
- денежных пополнений и списаний нет; баланс счёта ника не меняется
- для заказа выдаётся и сразу погашается жетон на бесплатный разбор; ранее выданные непогашенные жетоны не требуются и не списываются
- статус зависит только от наличия трека (см. бизнес-правила)
- если ника ещё не было, он создаётся вместе со счётом
- заказ появляется в очереди как новый, в одной группе с донатными
- возвращается созданный заказ

При невозможности выполнения:

- участник не администратор → отказ в доступе, заказ не создаётся
- нет ключа идемпотентности, ключ пустой или некорректный → отказ валидации, заказ не создаётся
- повтор с тем же ключом и тем же телом в течение часа → возвращается сохранённый успешный ответ, новый заказ не создаётся
- повтор с тем же ключом и другим телом → конфликт, новый заказ не создаётся
- повтор, пока первый запрос ещё не завершён → конфликт, новый заказ не создаётся
- ник пустой, длиннее 40 символов, комментарий длиннее 200, некорректный URL, длительность вне диапазона, задана только ссылка или только длительность → отказ валидации, заказ не создаётся
- нет ближайшего доступного стрима по правилу назначения → операция не выполняется, заказ не создаётся

## Бизнес-правила

1. Бесплатный заказ создаётся уже покрытым решением администрации. Денежная оплата этим use case не выполняется и для продвижения заказа не требуется.
2. Цена на заказе всё равно записывается как номинальная из настроек. Сумма к доплате при создании всегда 0, независимо от длительности трека.
3. После создания:
   - нет ссылки на трек → статус «предзаказ»
   - есть ссылка на трек → статус «ожидает взятия в работу»
4. Назначение стрима создания совпадает с донатным заказом:
   - у ника ещё не было ни одного заказа → ближайший доступный стрим любого типа
   - у ника уже есть хотя бы один заказ любого типа, включая отменённый → ближайший доступный донатный стрим
   - доступный стрим: идёт сейчас или запланирован на сегодня либо на будущее; из подходящих берётся с самой ранней датой
5. Ник ищется по нормализованному имени. Совпадение без учёта регистра — тот же зритель.
6. Жетон покрытия создаётся в момент оформления и сразу погашается на этот заказ. Отдельного заранее выданного жетона не нужно.
7. В очереди бесплатный заказ стоит вместе с донатными. Приоритет внутри группы — по фактически оплаченной сумме, затем по времени создания. При создании оплаченная сумма 0.
8. Повторный запрос: тот же администратор, тот же ключ идемпотентности и то же тело в течение часа возвращают прежний успешный ответ и не создают второй заказ, жетон и событие очереди.

## Различающие сценарии

- Если у ника нет заказов, бесплатный заказ сажается на ближайший стрим любого типа. Если заказы уже были, только на ближайший донатный стрим; отсутствие донатного стрима — ошибка, даже когда есть стримы другого типа.
- Если трека нет, заказ остаётся предзаказом. Если трек есть — сразу готов к взятию в работу, без ожидания оплаты.
- Бесплатный заказ не двигает деньги и не ждёт доплаты. Донатный заказ этим use case не создаётся.
- Бесплатный заказ попадает в донатную группу очереди. Внеочередной заказ этим use case не создаётся: у него другой тип, другое назначение стрима и отдельная категория очереди.
- Благотворительный и донатный заказы этим use case не создаются.

## Принятые ограничения

- Бизнес-ограничения: операцию выполняет только администратор; зритель сам заказ не создаёт.
- Технические ограничения: создание заказа, выдача и погашение жетона проходят в одной транзакции успешного запроса вместе с фиксацией идемпотентного ответа.
- Вне scope: доплата к уже существующему заказу, погашение заранее выданного жетона без создания нового, смена трека, взятие в работу, выполнение, заморозка, отмена, подробный разбор, создание заказов других типов.

## Основания спецификации

### Решения

- Пользователь запросил спецификацию «Создать бесплатный заказ» в `docs/use-cases/review-order`.

### Факты

- Операция уже реализована: `ReviewOrderController.CreateFree` → `CreateFreeHandler`.
- Доступ: `AuthorizeAdmins` (роли Composer и Moderator), обязательный заголовок идемпотентности.
- Заказ создаётся с типом Free, `payableAmount = 0`, статусом Preorder без трека или Pending при наличии трека. Пересчёт через `ReviewOrderEntity.Pay` при создании не вызывается.
- Покрытие: `UserEntitlementStore.CreateAndRedeemAdminCoverage` — новый жетон `FreeReviewOrder` и сразу погашение на заказ.
- Стрим: `HasOrders` по любому числу заказов ника, затем `GetNearestStream(Donation)` либо `GetNearestStream()` без типа.
- Очередь: `OrderPriorityManager` включает Free в одну группу с Donation; приоритет по `GetPaidPriorityAmount` (фактические платежи), затем по `CreatedAt`.
- После сохранения публикуется событие очереди `OrderCreated`.
- Валидация входа: `CreateRequestBase` и `CreateFreeRequest` (без суммы и канала).

### Предположения

- Текущая реализация отражает желаемый смысл, а не черновик, который нужно менять.
- Если ник создали, а ближайшего стрима нет, ник со счётом может остаться в системе без заказа.

### Открытые вопросы

- Нет вопросов, которые меняют наблюдаемый результат.

## Примеры приёмки

### Первый бесплатный заказ нового зрителя с треком

Дано:

- ника `viewer` нет
- номинальная цена 1000
- есть ближайший live-стрим любого типа
- донатных стримов нет

Когда:

- администратор создаёт бесплатный заказ: ник `viewer`, трек и длительность 180 секунд

Тогда:

- создан заказ типа «бесплатный» в статусе «ожидает взятия в работу»
- сумма к доплате 0
- денежных проводок нет
- выдан и погашен жетон на бесплатный разбор
- заказ привязан к этому ближайшему стриму
- заказ виден в очереди вместе с донатными

### Повторный бесплатный заказ того же зрителя

Дано:

- у ника `viewer` уже есть заказ
- ближайший донатный стрим есть
- ближайший стрим другого типа тоже есть и раньше по дате

Когда:

- администратор создаёт ещё один бесплатный заказ на `viewer`

Тогда:

- новый заказ привязан к ближайшему донатному стриму, а не к более раннему стриму другого типа

### Предзаказ без трека

Дано:

- есть доступный стрим по правилу назначения

Когда:

- администратор создаёт бесплатный заказ без ссылки и длительности

Тогда:

- заказ создан в статусе «предзаказ»
- сумма к доплате 0
- жетон выдан и погашен
- денежных проводок нет

### Нет донатного стрима для зрителя с историей

Дано:

- у ника уже есть заказ
- доступны только не-донатные стримы

Когда:

- администратор создаёт бесплатный заказ

Тогда:

- заказ не создаётся
- жетон не выдаётся

### Непогашенный жетон не требуется и не списывается

Дано:

- у ника есть непогашенный жетон на бесплатный разбор
- есть доступный стрим по правилу назначения

Когда:

- администратор создаёт бесплатный заказ

Тогда:

- заказ создан
- старый жетон остаётся непогашенным
- для нового заказа выдан и погашен отдельный жетон

### Повтор того же запроса

Дано:

- бесплатный заказ уже успешно создан с ключом `K`

Когда:

- тот же администратор повторяет тот же запрос с ключом `K` в течение часа

Тогда:

- возвращается прежний успешный ответ
- второй заказ и второй жетон не появляются

## Техническая привязка

- Точка входа: `POST api/ReviewOrder/CreateFree`
- Авторизация: `AuthorizeAdmins`
- Транзакционная граница: фильтр идемпотентности открывает транзакцию вокруг успешного выполнения; `SaveChanges` handler'а сохраняет заказ, жетон и погашение
- Идемпотентность: заголовок `Idempotency-Key`, запись на администратора и endpoint, TTL 1 час
- Изменяемые данные: `ReviewOrder`, `UserNickname` и `UserNicknameAccount` при первом появлении ника, `UserEntitlement`, `UserEntitlementRedemption`
- Публикуемые события: `OrderQueueEventChannel` / `OrderCreated`
- Требования к консистентности: заказ без погашенного жетона не должен сохраниться; повтор с тем же ключом не должен дать второй заказ
