# Use case: Выполнить заказ

## Полезный результат

Заказ разбора трека, который был в работе, становится выполненным. Фиксируется результат разбора — оценка трека. Заказ больше не занимает слот «в работе» и отображается среди выполненных.

## Участник и момент запуска

- Участник: администратор
- Триггер: администратор завершает разбор по заказу, который сейчас в работе, и указывает оценку трека
- Предусловия: заказ существует

## Входные данные

- `ReviewOrderId` — идентификатор заказа; должен быть больше нуля
- `Rating` — оценка трека; целое число от 0 до 26 включительно

## Наблюдаемый результат

При успехе:

- статус заказа становится «выполнен»
- фиксируется момент выполнения
- создаётся результат разбора, связанный с этим заказом: оценка равна переданной, автор — текущий администратор
- у заказа ровно один результат разбора
- очередь обновляется: заказ переходит в выполненные
- возвращаются актуальный заказ и идентификатор созданного разбора

При невозможности выполнения:

- заказ не найден → операция отклоняется, состояние не меняется
- статус заказа не «в работе» → операция отклоняется с ошибкой «Невозможно выполнить заказ», состояние не меняется
- `ReviewOrderId` не задан или не больше нуля → запрос отклоняется на валидации, состояние не меняется
- оценка не задана или вне диапазона 0–26 → запрос отклоняется на валидации, состояние не меняется

## Бизнес-правила

1. Выполнить можно только заказ в статусе «в работе».
2. Тип заказа на возможность выполнения не влияет: любой заказ в работе выполняется одинаково.
3. Живой стрим в момент выполнения не требуется.
4. Заморозка заказа на выполнение не проверяется: заказ в работе заморозить текущими операциями нельзя.
5. Оценка обязательна и принадлежит шкале 0–26.
6. Результат разбора при выполнении содержит только оценку и автора. Ссылка на видео разбора и привязка разбора к треку этим use case не задаются.
7. Повторный запрос: если заказ уже выполнен, операция отклоняется с ошибкой «Невозможно выполнить заказ». Существующий разбор и оценка не меняются, новый разбор не создаётся.

## Различающие сценарии

- Если заказ в работе, система создаёт разбор с переданной оценкой и переводит заказ в «выполнен».
- Если заказ уже выполнен, система отказывает так же, как для любого другого статуса кроме «в работе». Оценка в запросе не применяется.

## Принятые ограничения

- Бизнес-ограничения: оценка по шкале 0–26; повторный вызов по выполненному заказу — ошибка
- Технические ограничения: операция доступна только администратору; HTTP-идемпотентность по ключу не используется
- Вне scope: взятие заказа в работу; отмена; изменение оценки или содержимого разбора после выполнения; привязка разбора к треку; ссылка на видео разбора; денежные операции

## Основания спецификации

### Решения

- Описать use case «Выполнить заказ» в `docs/use-cases/review-order`
- Другие спецификации use case не использовать как основание
- Если заказ уже выполнен, повторный вызов должен приводить к ошибке, а не к успеху

### Факты

- Точка входа: `ReviewOrderController.Complete`
- Доменный метод выполняет заказ только из статуса `InProgress`; иначе ошибка «Невозможно выполнить заказ»
- Текущий обработчик при статусе `Completed` возвращает заказ без ошибки — это расходится с принятым решением
- При выполнении создаётся `Review` с оценкой и текущим администратором; у заказа и разбора связь один к одному
- После сохранения публикуется событие очереди `OrderCompleted`
- Оценка валидируется на входе как целое число от 0 до 26
- Атрибут HTTP-идемпотентности на этой операции отсутствует
- Разбор при создании не связывается с треком и не получает ссылку на видео

### Предположения

- Текст ошибки для уже выполненного заказа совпадает с отказом для остальных недопустимых статусов: «Невозможно выполнить заказ»

### Открытые вопросы

- Нет вопросов, меняющих наблюдаемый результат

## Примеры приёмки

### Заказ в работе выполняется

Дано:

- существует заказ в статусе «в работе»
- разбора по заказу ещё нет

Когда:

- администратор выполняет заказ с оценкой 18

Тогда:

- статус заказа — «выполнен», момент выполнения зафиксирован
- создан разбор с оценкой 18, автор — этот администратор
- заказ отображается среди выполненных в очереди
- в ответе есть заказ и идентификатор созданного разбора

### Повторное выполнение уже выполненного заказа

Дано:

- заказ уже выполнен
- у заказа есть разбор с оценкой 10

Когда:

- администратор снова выполняет тот же заказ с оценкой 20

Тогда:

- операция отклоняется с ошибкой «Невозможно выполнить заказ»
- статус, момент выполнения и оценка разбора не меняются
- новый разбор не создаётся

### Заказ ещё не в работе

Дано:

- заказ в статусе «ожидает взятия в работу»

Когда:

- администратор пытается выполнить заказ с оценкой 12

Тогда:

- операция отклоняется с ошибкой «Невозможно выполнить заказ»
- статус заказа не меняется, разбор не создаётся

### Заказ не найден

Дано:

- заказа с указанным идентификатором нет

Когда:

- администратор пытается выполнить заказ

Тогда:

- операция отклоняется
- новые данные не создаются

### Оценка вне шкалы

Дано:

- существует заказ в статусе «в работе»

Когда:

- администратор передаёт оценку 27

Тогда:

- запрос отклоняется на валидации
- статус заказа не меняется, разбор не создаётся

## Техническая привязка

- Точка входа: `POST api/ReviewOrder/Complete`
- Авторизация: только администратор
- Транзакционная граница: одно сохранение контекста БД
- Идемпотентность: повтор по уже выполненному заказу должен завершаться ошибкой; HTTP-ключ идемпотентности не применяется
- Изменяемые данные: `ReviewOrder` (статус, `CompletedAt`, связь с разбором); новая запись `Review`
- Публикуемые события: `OrderQueueUpdateType.OrderCompleted`
- Требования к консистентности: разбор и перевод заказа в «выполнен» сохраняются вместе
